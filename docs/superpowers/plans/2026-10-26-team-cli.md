# `ledge team` and `ledge close` on the action registry — Implementation Plan (#93)

2026-10-26. **Goal:** give agents and scripts the team operations the Desktop already has, and `ledge close` (#75 is
settled here), as a thin layer over the action registry of #94: the CLI parses argv against `ACTIONS[id].args`, sends
`action.run`, and the daemon runs the same `resolve` → message → `handle` as the chat's generic card. No rule is written
twice.

**Base:** branch `feat/team-cli` from `feat/action-registry` (b4dbc360); rebased on Lu's fixes of #94 (t28f438).
**Spec:** [action registry §2.1](../specs/2026-10-26-action-registry-design.md), issue #93.

## Waiting for the user — not decided here

- **(a) Who may run a destructive action from an agent session** (`by` a session, not the user). Until then, one guard
  function, `runGuard(risk, by)` in `daemon/actions.ts`, set to the strictest: a session never runs a `destructive`
  action (today `team.dissolve`, `task.cancel`, `session.decide` accept), with a clear message (« demande à
  l'utilisateur »). The user (a terminal Ledge did not launch, no `by`) runs it with `--yes`. Note: `by` is what the
  CLI's environment says (`LEDGE_SESSION`), as for `ledge task`: a courtesy rule against an agent's mistake, not a
  security boundary (any local client can already send `team.dissolve`).
- **(b) Renaming a team**: not added.
- **(c) `ledge team add <équipe> <@rôle> [--tool] [--model] [--effort]`** (launch a new agent straight into a seat): not
  added. It would need a registry entry `team.seat` `{team, role, tool?, model?, effort?}` (reversible) and a daemon
  path: `launch({ cwd: team.cwd, tool, role, team: team.id, model, effort })` already seats a session at launch (the
  `team` field of `LaunchReq`), so the op is mostly a resolver (the team live, the role known in its folder, the seat
  free or the role repeatable) plus `toClient` → a new `team.seat` client message answered by `team.updated`.

## Tasks

### Task 1 — `action.run` / `action.result` (protocol)
- `ClientMessage` `action.run { rid, by?, action: ActionId, args, confirmed?: true }`; `ServerMessage`
  `action.result { rid, action, row?: ChatAction, reason?, code?: 'confirm_required' | 'refused' | 'agent' }`, plus
  `path?` (a `team.save`'s template). Tests in `messages.test.ts`.

### Task 2 — the daemon runs an action (`daemon/actions.ts`, `server.ts`)
- `session.close` gets a resolver for the CLI only (writable session, not the caller itself: an agent waiting on its
  own close would be killed at the end of the wait); it applies through `closeSession`. It stays out of
  `GENERIC_ACTIONS`: the chat keeps its close card.
- `runGuard(risk, by)`: (a) above.
- `action.run`: resolve (refused → `action.result` with `reason`, code `refused`) → guard (code `agent`) →
  `destructive` without `confirmed` → code `confirm_required` with the row → apply as `actOnCard` does → `action.result`
  with the row (`reason` on the handler's `error`). Tests in `teams-server.test.ts` style.

### Task 3 — `ledge team` verbs and `ledge close` (`cli/team.ts`, `cli/run.ts`, `cli/index.ts`)
- `join <équipe> <session> <@rôle>`, `leave <équipe> <session>`, `resume <équipe>`, `dissolve <équipe>
  [--close-sessions] [--yes]`, `save <équipe> <nom>`, `ledge close <session>`; argv → args, checked with
  `ACTIONS[id].args`. `--close-sessions`: the live seats are read before the dissolve, then each closed with
  `session.close` (two registry actions in a row, no rule of its own).
- `up --seat role[:tool]` (repeatable) → `team.launch` with `seats` (ad hoc, a template or seats, not both).
- `--json` on `list` and every operation: the `action.result` (or `{templates, roles, problems, teams}`) as one line.
- Tests: argv parsing, the output lines, a fake daemon for the round trip.
